# Stored procedures

All fake data in this project is generated by PL/pgSQL procedures in the `fake_users` database. The Python app only calls `generate_batch` and shows the result.

Almost every procedure takes the same four arguments:

- `p_locale text` - locale code from the `locales` table (`uz_UZ` or `kk_KZ`)
- `p_seed bigint` - the seed entered by the user
- `p_batch integer` - batch number, starting from 0
- `p_position integer` - position of the user in the batch, from 0 to 9

The procedures return values through OUT parameters. In `CALL` you write `NULL` for every OUT parameter and get the values back as one row.

The result depends only on these arguments and on the rows in the lookup tables. There is no `setseed()` and no saved state, so the same locale, seed, batch and position always give the same user.

## random_uniform

```
random_uniform(p_locale, p_seed, p_batch, p_position, p_field text, OUT result double precision)
```

Returns a pseudo-random number between 0 and 1 (never exactly 0 or 1). All other random procedures use it.

`p_field` is a label for the value we need, for example `'city'` or `'phone_format'`. Every field has its own label, so one user gets independent numbers for the city, the street, the phone and so on.

How the number is made:

1. The five arguments are put into a JSON array and turned into text, for example `["uz_UZ", 42, 0, 3, "city"]`.
2. `md5` of this text gives 32 hex characters.
3. The first 13 hex characters are 52 bits, so they give an integer `n` from 0 to 2^52 - 1.
4. The result is `(n + 0.5) / 2^52`.

Adding 0.5 keeps the result away from 0 and 1. This matters for `random_normal`, which takes `ln(u)`, and `ln(0)` does not exist.

```sql
CALL random_uniform('uz_UZ', 42, 0, 3, 'city', NULL);
```

Result: `0.5545524668837704`.

## random_integer

```
random_integer(p_locale, p_seed, p_batch, p_position, p_field text, p_min integer, p_max integer, OUT result integer)
```

Returns a whole number from `p_min` to `p_max`, both included. It takes `u` from `random_uniform` with the same `p_field` and returns `p_min + floor(u * (p_max - p_min + 1))`. Because `u` is always less than 1, the result is never bigger than `p_max`. If `p_min` or `p_max` is NULL, or `p_min > p_max`, it raises an error.

The generators use it to pick a row from a lookup table. They count the rows for the locale, call `random_integer(..., 0, count - 1)` and read the row with `ORDER BY id LIMIT 1 OFFSET` this number. The order by `id` does not change, so the same number always gives the same row.

```sql
CALL random_integer('uz_UZ', 42, 0, 3, 'house_number', 1, 200, NULL);
```

Result: `188`.

## random_normal

```
random_normal(p_locale, p_seed, p_batch, p_position, p_field text, p_mean double precision, p_stddev double precision, OUT result double precision)
```

Returns a normally distributed number with mean `p_mean` and standard deviation `p_stddev`. It raises an error if the mean is NULL or the standard deviation is NULL or negative.

It uses the Box-Muller transform. Two uniform numbers `u1` and `u2` come from `random_uniform` with the labels `p_field || '_u1'` and `p_field || '_u2'`. Then

```
z = sqrt(-2 * ln(u1)) * cos(2 * pi * u2)
```

has the standard normal distribution N(0, 1), and the procedure returns `p_mean + p_stddev * z`.

```sql
CALL random_normal('uz_UZ', 42, 0, 3, 'height_z', 176, 7, NULL);
```

Result: `170.83635333355613`.

## generate_name

```
generate_name(p_locale, p_seed, p_batch, p_position, OUT name text, OUT sex text)
```

Returns a full name and the sex (`female` or `male`). The name is built in four steps:

1. The sex is chosen 50/50 (label `gender`).
2. A first name is picked from `first_names` with the same locale and gender (label `first_name`).
3. A last name is picked from `last_names` with the same locale and gender (label `last_name`). The table has both forms of a last name, for example Karimov for men and Karimova for women.
4. With probability 1/2 (label `use_title`) a title from `titles` with the same locale and gender is put in front of the name (label `title`). Now the titles are `Mr.` and `Ms.`.

So a name looks like `Ms. Natija Aliyeva` or `Natija Aliyeva`. Middle names and patronymics are not generated.

```sql
CALL generate_name('uz_UZ', 42, 0, 0, NULL, NULL);
```

Result: `Ms. Natija Aliyeva`, `female`.

## generate_address

```
generate_address(p_locale, p_seed, p_batch, p_position, OUT address text)
```

Returns an address as one string. The city is picked from `cities` (label `city`) and the street from `street_names` (label `street`). The house number is from 1 to 200 (label `house_number`) and the apartment number is from 1 to 150 (label `apartment_number`). The words for street, house and apartment are taken from `locales`: `ko'chasi`, `uy`, `xonadon` for `uz_UZ` and `koshesi`, `ui`, `pater` for `kk_KZ`.

One of three formats is chosen (label `address_format`):

```
Tashkent, Amir Temur ko'chasi, 15-uy
Amir Temur ko'chasi 15, Tashkent
Tashkent, Amir Temur ko'chasi, 15-uy, 23-xonadon
```

```sql
CALL generate_address('uz_UZ', 42, 0, 0, NULL);
```

Result: `Asaka, Ibn Sino ko'chasi, 137-uy, 32-xonadon`.

## generate_coordinates

```
generate_coordinates(p_locale, p_seed, p_batch, p_position, OUT latitude double precision, OUT longitude double precision)
```

Returns a point in degrees that is uniformly distributed on the sphere. `u` and `v` come from `random_uniform` with the labels `latitude` and `longitude`:

```
latitude = degrees(asin(2 * u - 1))
longitude = 360 * v - 180
```

Latitude cannot simply be `180 * u - 90`. A band around the equator has a much bigger area than a band of the same height near a pole. The area of the sphere between the equator and some latitude is proportional to the sine of this latitude, so for a uniform point the sine of the latitude must be uniform on [-1, 1]. `2 * u - 1` is uniform on (-1, 1), and `asin` turns it into the latitude. With a uniform latitude there would be too many points near the poles.

This is easy to check: about half of the points must have |latitude| < 30, because sin(30 degrees) = 0.5. With a uniform latitude it would be only one third. Longitude can be uniform because the sphere looks the same in every direction around the axis.

```sql
CALL generate_coordinates('uz_UZ', 42, 0, 0, NULL, NULL);
```

Result: `-13.832224468023417`, `127.07743635252143`.

## generate_attributes

```
generate_attributes(p_locale, p_seed, p_batch, p_position, p_sex text, OUT height_cm numeric, OUT weight_kg numeric, OUT hair_color text)
```

Returns height, weight and hair color. `p_sex` must be `male` or `female`, otherwise it raises an error.

Height and weight are normal, with different parameters for men and women:

| Sex | Height, cm | Weight, kg |
|---|---|---|
| male | mean 176, sd 7 | mean 76, sd 12 |
| female | mean 163, sd 6.5 | mean 62, sd 10 |

Weight is linked to height. The procedure takes two independent standard normal numbers, `z_h` (label `height_z`) and `z_w` (label `weight_z`), and computes

```
height = height_mean + height_sd * z_h
weight = weight_mean + weight_sd * (0.55 * z_h + sqrt(1 - 0.55 * 0.55) * z_w)
```

The value in brackets is still N(0, 1), but its correlation with `z_h` is 0.55. So taller people are heavier on average, but not always. Both values are rounded to 0.1.

Hair color is a discrete value. It is picked from `hair_colors` for the same locale (label `hair_color`).

```sql
CALL generate_attributes('uz_UZ', 42, 0, 0, 'female', NULL, NULL, NULL);
```

Result: `157.5`, `52.9`, `Light brown`.

## generate_phone

```
generate_phone(p_locale, p_seed, p_batch, p_position, OUT phone text)
```

Returns a phone number. The country code comes from `phone_settings` (998 for Uzbekistan, 7 for Kazakhstan). The operator code is picked from `phone_operators` for the locale (label `phone_operator`). If a locale has no operators, `phone_settings.operator_code` is used. The subscriber number has 7 digits, from 0000000 to 9999999 (label `phone_number`).

One of three formats is chosen (label `phone_format`):

```
+998901234567
+998 90 123-45-67
+998 (90) 123 45 67
```

```sql
CALL generate_phone('kk_KZ', 42, 0, 1, NULL);
```

Result: `+7 705 351-78-03`.

## generate_email

```
generate_email(p_locale, p_seed, p_batch, p_position, OUT email text)
```

Returns an email for the same person that `generate_name` gives.

1. It calls `generate_name` with the same arguments, so it gets the same name.
2. It takes the last two words of the name, the first name and the last name. The title is skipped.
3. It joins them with a dot, makes them lower case and removes all characters except `a-z`, `0-9` and the dot. For example `Jo'rayev` becomes `jorayev` and `Shara-Shyryngul` becomes `sharashyryngul`.
4. It adds a number from 100 to 999 (label `email_suffix`).
5. It adds a domain from `email_domains` for the locale (label `email_domain`).

```sql
CALL generate_email('uz_UZ', 7, 5, 5, NULL);
```

Result: `nizom.jorayev162@icloud.com` (the name is `Nizom Jo'rayev`).

## generate_user

```
generate_user(p_locale, p_seed, p_batch, p_position, OUT name text, OUT sex text, OUT address text, OUT latitude double precision, OUT longitude double precision, OUT height_cm numeric, OUT weight_kg numeric, OUT hair_color text, OUT phone text, OUT email text)
```

Returns one full user. It calls `generate_name`, `generate_address`, `generate_coordinates`, `generate_attributes`, `generate_phone` and `generate_email` with the same four arguments. The sex from `generate_name` is passed to `generate_attributes`.

```sql
CALL generate_user('kk_KZ', 7, 0, 0, NULL, NULL, NULL, NULL, NULL, NULL, NULL, NULL, NULL, NULL);
```

Result: `Ms. Tatti Saduakasova`, `female`, `Aliya Moldagulova koshesi 184, Rudny`, `-25.51940062679049`, `127.07492385400809`, `172.8`, `71.9`, `Light brown`, `+77757951516`, `tatti.saduakasova185@mail.ru`.

## generate_batch

```
generate_batch(p_locale text, p_seed bigint, p_batch integer)
```

Makes 10 users (positions 0 to 9) and writes them to the temporary table `generated_users`. It returns nothing itself. The table has the columns `position`, `name`, `sex`, `address`, `latitude`, `longitude`, `height_cm`, `weight_kg`, `hair_color`, `phone` and `email`. The procedure creates the table if it does not exist and clears it before writing.

It raises an error if the seed is NULL, the batch is less than 0 or the locale is not in `locales`.

The number of a user is `p_batch * 10 + p_position`, so the next batch is just `p_batch + 1`.

`generated_users` is a temporary table, it is visible only in the connection that created it. So `CALL` and `SELECT` must run in the same connection. `fetch_batch` in `db_code.py` does it this way.

```sql
CALL generate_batch('uz_UZ', 42, 0);
SELECT * FROM generated_users ORDER BY position;
```

## Lookup tables

Each kind of data is stored in one table with a `locale_code` column, there are no separate tables for each language.

| Table | Main columns | Rows |
|---|---|---|
| `locales` | `locale_code`, `locale_name`, `street_word`, `house_word`, `apartment_word` | 2 |
| `first_names` | `locale_code`, `name`, `gender` | 6033 |
| `last_names` | `locale_code`, `surname`, `gender` | 582 |
| `titles` | `locale_code`, `title`, `gender` | 4 |
| `cities` | `locale_code`, `city_name` | 80 |
| `street_names` | `locale_code`, `street_name` | 100 |
| `hair_colors` | `locale_code`, `color_name` | 16 |
| `phone_settings` | `locale_code`, `country_code`, `operator_code` | 2 |
| `phone_operators` | `locale_code`, `operator_code` | 21 |
| `email_domains` | `locale_code`, `domain_name` | 10 |

`uz_UZ` has 605 male and 560 female first names and 135 last names for each gender, which gives about 157 000 different first and last name pairs. `kk_KZ` has 3479 male and 1389 female first names and 156 last names for each gender, about 759 000 pairs. In a sample of 100 000 or 1 000 000 users some names repeat, like in real life, but with the address, phone and email a whole user practically never repeats.

A row is chosen by its place in the list for the locale. If rows are added to or removed from an existing locale, the same seed will give other users.

Data sources:

- Uzbek first names: [azamroziboyev/uzbek_names](https://github.com/azamroziboyev/uzbek_names), public domain according to the repository README.
- Kazakh first names: [KazPER](https://github.com/yeshpanovrustem/KazPER) by Rustem Yeshpanov, CC BY 4.0.
- Uzbek operator codes: [Telephone numbers in Uzbekistan](https://en.wikipedia.org/wiki/Telephone_numbers_in_Uzbekistan) on Wikipedia.
- Kazakh operator codes: [mimesis](https://github.com/lk-geimfari/mimesis), `datasets/kk/person.json`, MIT license.
- Last names, cities, streets, titles, hair colors and email domains were collected for this study project. They are not an official list.

## Adding a new locale

The procedures do not need any changes. For example, for `de_DE`:

1. Add a row to `locales` with the code, the name and the words for street, house and apartment. The house and apartment words can be NULL.
2. Add rows with `locale_code = 'de_DE'` to `first_names` and `last_names` (for both genders), `titles`, `cities`, `street_names`, `hair_colors`, `phone_operators` and `email_domains`, and one row to `phone_settings`.
3. Add the locale to `LOCALES` in `app.py`, so it appears in the list on the page.

The email keeps only the letters a-z, so letters like `ü` or `ß` are removed from it. For such a language it is better to add a transliteration step to `generate_email` (for example `ü` to `ue`).
